# 红隼（Kestrel）

- 显示名：红隼
- 作者：[Anchorite-no](https://github.com/Anchorite-no)。代码由 Claude（Anthropic 的 AI 模型）在作者指导下编写和迭代。
- 文件：`bot.js`，单文件，约 4.4 万字符，不依赖 `lab` 以外的任何东西。

导入：

```powershell
node --import tsx scripts/import-bot.ts bots/kestrel/bot.js '红隼'
```

## 策略

对局中的输入只有 `lab.observe()`、`lab.act()`、`lab.fire()` 返回的 JPEG，输出只有移动、旋转、瞄准和单发请求。

**感知。** 脚本自带一个 JPEG 局部解码器。熵码要顺序读完，但只对用得到的块做反变换：两车周围、HUD 的血条和热量条，以及亮度相对背景突然变亮的块（弹丸）。一帧的解码加识别约 1.3 毫秒，所以控制循环能跑到 60 次每秒，每帧新画面都能用上。从像素里读出的量有：两车的位置和装甲相位（由四块装甲的像素拟合）、炮管朝向、弹丸位置和归属、双方血量和热量、是否在准备阶段。

**瞄准。** 不假设对手匀速。脚本持续统计"对手在当时的速度方向上，T 秒后实际移动了多少"，按预测时长分桶保存样本。会随机变向的对手，位移分布是多峰的，瞄平均值恰好最容易打空，所以直接在样本分布上找命中概率最高的落点。落点是否命中由一个几何函数判定，它按装甲相位和车体转速逐步推进弹丸，区分打中装甲、被车体挡下和落空。

**防御。** 每个控制周期在 25 个平移方向里选代价最低的，代价包含来弹威胁、贴墙、与对手的距离和一个随机游走方向。平移躲不开时加入旋转候选：把车体转到让来弹打在车体而不是装甲上的相位。150 像素以内来不及看见弹丸再反应，这时把对手炮线当作一发随时会来的弹，提前摆好相位。

**交战距离和开火。** 按开火距离分三段统计自己的实际命中率（由对手血条的下降归因）。
- 远距离打得中的对手：保持约 300 像素持续射击。
- 远距离打不中的对手（通常是它也会用装甲相位化解）：停火让热量降下来，等对手热量条偏高时突入 150 像素以内连发，热量接近上限后撤出。这个距离上弹丸飞行时间短于对手的反应时间。
- 僵持时只用"凉透后本来会浪费掉"的那点热量余量打冷枪。

热量用一个只会偏高的上界来估计（每次请求都当作出膛，再用 HUD 读数向下校正），目的是任何情况下都不过热。

## 预期行为

- 准备阶段原地不动，炮塔指向对手。
- 开局后立刻开始不规则变向，先在远处试射十几发。
- 之后要么站在约 300 像素处持续射击，要么反复"远处停火等待 → 冲近连发 → 撤出"。
- 被瞄准时会短暂原地转动车体，这是在调整装甲相位，不是卡住。
- 对局结束后接口调用开始失败，脚本会在约 0.2 秒内自行正常退出。
- 脚本不读写文件、不联网、不创建子进程或 Worker；每局调用约 4000 次（宿主上限 30000）。

## 已知局限

- **没有在 DSH Desktop 界面里实际跑过**，只在上述无界面宿主上测试。
- **没有在 Deno 受限运行时里跑过**（`contest-duel` 那条路径，本机没有 Deno）。代码只用了标准 JavaScript 和 `performance.now()`，按理兼容，但未验证。
- 画面宽度小于默认的 960，或供图帧率低于 30 时，识别精度和反应时间会变差。半宽画面和 15 帧每秒在压力测试里仍然获胜，更极端的设置没有测过。
- 对水平相当的对手没有优势，结果接近五五开。
- 机器负载过高、供图掉帧或控制循环变慢时，表现会明显变差。本地评测是 12 局并行跑的，CPU 争用会让结果有波动。
- 单发伤害调得极高（两三发致命）时运气成分很大，压力测试里攻击力 100 的那组出现过 1 负。
- 样本量有限，每组 2 到 20 局，表里的胜率不应读成精确概率。
